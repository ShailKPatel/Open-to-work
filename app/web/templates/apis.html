Stored keys

Keys for the same provider back each other up. The active one is tried first; if it runs out of quota or gets rejected partway through a job, the next one takes over that same request and the job carries on. A job only stops once every key for the provider is spent, and it says which key failed and why. A key that is out of quota is tried last rather than skipped, since quotas reset.

Waiting on a quota reset

These keys hit a limit that resets by itself. Each one is checked again when the app starts and every half hour after that, once the wait for its own limit is over: a per-minute burst comes back in a minute, a used-up daily allowance when the provider's day rolls over. A key that answers again goes straight back into normal rotation. Nothing here needs you to do anything; the button above only skips the wait.

A check confirms the key still works, not how much quota is left: no provider gives that away for free. Once the wait is over the key is treated as good again, and the next real call is what settles it.

Needs your attention

The provider rejected these keys outright, or shut them off: a wrong or deleted key, a suspended project, billing not set up, or the provider's API never enabled. Waiting changes nothing, so these are never rechecked on their own. Fix the key in the provider's console, or replace it here, then use the button above (or Check now on the key) to look again.
